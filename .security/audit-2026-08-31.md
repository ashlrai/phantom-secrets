## Fix-forward disposition

| ID | v0.7.0 finding | v0.7.1 source disposition |
|---|---|---|
| S-01 | `PHANTOM_API_URL` could redirect the OS-keychain cloud bearer to an arbitrary HTTPS or local origin. | Cloud authentication is pinned to `https://phm.dev/api/v1`; shipped runtime origin overrides fail before cloud network access. |
| S-02 | Protected connection strings were copied as plaintext into the untrusted `phantom exec` child environment. | Agent execution refuses protected connection-string services pending a protocol-aware broker. No plaintext connection string is injected into the child. |
| S-03 | Exact-match response redaction embedded a prefix, or a complete short value, in the replacement and warning and could panic on a non-ASCII byte boundary. | Exact vault matches use the value-independent label `[REDACTED:vault-secret]`; no label is derived from secret bytes or characters. Short and Unicode regression tests pass. |
| S-04 | Repository-controlled `.phantom.toml` selected both the vault namespace and the credential destination. | Local vault/shadow/scheduler namespaces use a domain-separated SHA-256 digest of the canonical config directory independently of the committed portable cloud/team project ID, and agentic proxy startup accepts only exact built-in route definitions. The former collision-selectable 64-bit namespace is not reopened automatically. Custom or altered destinations fail closed. |
| S-05 | Unvalidated project IDs could escape the fallback vault directory. | File-vault construction validates the project ID before constructing `.vault`, lock, temporary, or legacy paths. |
| S-06 | Nonstandard credential headers could follow cross-origin redirects; oversized streamed requests could reach upstream as successful truncations; buffered responses were unbounded. | Upstream redirects are disabled. Requests are completely accepted under a hard byte cap before upstream dispatch, and buffered upstream responses are capped before redaction. |
| S-07 | Unsigned records appended after the signed audit era could pass verification as legacy and contaminate statistics; whole-log erasure could appear clean while an authenticated head remained. | A signed-era marker and retained head make unsigned modern entries, marker removal, log replacement, and retained-head erasure fail closed; statistics consume only verified records. |
| S-08 | A runtime mock-rotation switch plus alternate Stripe base could redirect a vaulted refresh credential. | Mock rotation and alternate credential-bearing endpoints are compiled only for hermetic tests; shipped binaries have no runtime environment escape hatch. |
| S-09 | Mutable GitHub login identity enabled team-invite impersonation; device-code issuance used a racy global limit; public keys received only a length check. | The candidate adds server-owned normalized identity, strict migration-time reconciliation from exactly one verified GitHub identity, normalized uniqueness, an atomic per-client/global issuance RPC, and canonical X25519 public-key validation. The complete isolated migration chain, privilege model, rollback cases, and poisoned-row repair passed. Applying and accepting the migration in production remains a separate deployment gate. |
| S-10 | OAuth/device query values could be retained and captured in pageview analytics; browser headers lacked CSP/isolation controls. | Device approval state no longer uses query-bearing URLs, analytics captures pathname-only pageviews, and the candidate adds CSP plus isolation headers. |
| S-11 | Installers and self-update authenticate release bytes only through checksums hosted with those bytes. | GitHub immutable releases and attestations strengthen publisher evidence, but installers and self-update still do not verify attestations directly. Independent signing remains open. |

## Remaining product and security limitations

- Repository-defined/custom proxy routes are intentionally unavailable in
  agentic sessions. Supporting private gateways safely requires a future
  machine-local, trusted-terminal approval record bound to the exact origin and
  project.
- Protected connection strings are intentionally unavailable to agent child
  processes until Phantom has a protocol-aware database broker.
- The collision-resistant local namespace deliberately does not reopen the
  former 64-bit namespace. Offline-only `0.7.0` users must create an encrypted
  trusted-terminal export before upgrade and import it afterward; cloud/team
  users can restore through an encrypted pull.
- `.phantom.toml` remains unsigned. The new binding and exact-route checks close
  credential selection/redirection, but repository tampering can still deny a
  session or change unrelated settings.
- A root/admin attacker, compromised same-user session, malicious debugger, or
  replaced Phantom binary remains outside the local confidentiality boundary.
- Local audit HMAC state does not prove deletion of both the log and its local
  checkpoint without externally anchored evidence.
- Team offboarding does not revoke access to vault versions encrypted to a
  former member before removal. Affected credentials still require rotation.
- Provider issuance source does not prove a live provider application, consent,
  renewal, or customer workflow. Remote provider-grant revocation remains
  fail-closed and unavailable where the provider path is not wired.
- Production engineering execution remains deny-all pending coherent signed
  Locus authority, peer-authenticated native transport, OS confinement, trusted
  handle minting, replay anchoring, and correlated trusted receipts.
- GitHub attestations are not verified by the direct installers or self-updater.
  macOS notarization, Windows Authenticode, independent signatures, and
  exact-archive acceptance on all six targets remain open.

## Decision

The dirty `v0.7.1` source candidate materially addresses the audited credential
boundaries and closes the identified source P0/P1 issues under focused and
isolated-database regression coverage. It is **not yet production-ready or
released**. Production claims require the exact-commit full gates, protected
branch and CodeQL evidence, live migration, deployment, immutable artifacts,
native acceptance, and authenticated workflow acceptance listed above.
